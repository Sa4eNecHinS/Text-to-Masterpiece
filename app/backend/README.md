## Ограничение параллельной генерации

`POST /Text-to-Masterpiece/generate` удерживает две PostgreSQL session-level
advisory locks от проверки Token Bucket до сохранения изображения и истории
(или обработки ошибки): lock владельца, затем один глобальный слот. Повторный
запрос того же проверенного владельца получает **409**:

```json
{"detail": "Image generation is already in progress."}
```

Глобальный предел задаётся `AI_MAX_CONCURRENT_GENERATIONS=5` в `.env`.
При запуске проверяется положительное целое значение в пределах PostgreSQL int32.
Если все слоты заняты, другой владелец получает **503**:

```json
{"detail": "Server is busy. Please try again later."}
```

В обоих случаях Token Bucket и дневной бюджет не расходуются, Cloudflare не
вызывается. При 503 уже полученный lock владельца освобождается. Frontend
показывает сообщение без автоматической повторной отправки.
Проверка модели и создание/проверка гостевой идентичности выполняются
до захвата; cookie нового гостя сохраняется и при последующих ошибках. История
по-прежнему создаётся только при успешной генерации.

`database/generation_lock.py` использует одно закреплённое соединение из
существующего async Engine для обеих блокировок. После owner lock менеджер
неблокирующе перебирает слоты `1..AI_MAX_CONCURRENT_GENERATIONS` через
`pg_try_advisory_lock(1487001, slot)` до первого успеха. Двухкомпонентное
пространство ключей PostgreSQL не пересекается с int64-ключами владельцев.
После захвата выполняется COMMIT: блокировки сохраняются, но открытой транзакции
во время HTTP-запроса нет. Перед обращением к Cloudflare соединение проверяется
без переподключения. Проверка повторяется перед B2 PUT и после его завершения,
до сохранения результата. При потере lock после PUT выполняются rollback и
компенсирующее удаление объекта, запрос получает 503. Проверка не является fencing:
потеря сессии после неё всё ещё возможна. При выходе освобождаются именно полученный глобальный слот,
затем lock владельца. Проверяются оба результата unlock; при ошибке или
неизвестном состоянии соединение инвалидируется, а не возвращается в pool с
потенциально оставшимися блокировками. Очистка защищена от отмены запроса.

Ключ — signed int64 из первых восьми байт SHA-256 от namespace, типа владельца
(`user` / `guest`) и его внутреннего ID из БД. Не используется IP или непроверенный
ID из тела запроса. Вероятность коллизии мала, но математической уникальности нет.

### Эксплуатационные ограничения

- Блокировки общие для workers, подключённых к одной базе PostgreSQL. У всех
  workers должно быть одинаковое `AI_MAX_CONCURRENT_GENERATIONS`; изменение
  лимита требует согласованного перезапуска, без смешивания старых/новых значений.
- Нужны прямые PostgreSQL-соединения или session pooling. Transaction/statement
  pooling (например, соответствующий режим PgBouncer) несовместим с session locks.
- Каждая активная генерация занимает одно соединение pool для обеих блокировок
  и до одного дополнительного для SQL. Rate limit, бюджет и сохранение выполняются
  последовательно; во время Cloudflare/B2 SQL-транзакция не удерживается.
  Пять генераций требуют 5–10 соединений; ещё по одному запросу авторизации,
  истории и моделей дают верхнюю потребность 13. При перегрузке операции ждут
  свободное соединение, затем возможен pool timeout. Новый runtime Engine или
  отдельный pool не создаются.
- Запрос к Cloudflare ограничен общим deadline `asyncio.timeout(60.0)` вокруг
  всего HTTP-обращения, включая чтение ответа и закрытие клиента. Отдельно
  сохранён `httpx.Timeout(60.0)` для сетевых операций; он не заменяет общий deadline.
- Потеря PostgreSQL-соединения снимает lock; при обнаружении до HTTP-вызова
  запрос завершается 503. Гарантировать владение после потери соединения нельзя.
- Аварийное завершение backend или timeout не гарантируют остановку уже начатых
  вычислений на стороне Cloudflare. Advisory lock — не механизм отмены провайдера.
- Гость определяется существующей cookie; запросы без общей гостевой идентичности
  считаются разными гостями. Frontend инициализирует гостевую сессию до генерации.

## Render Free / Neon: конфигурация соединений

Production Docker-команда явно запускает `uvicorn ... --workers 1`, независимо
от `WEB_CONCURRENCY`. При запуске без Docker также указывайте `--workers 1`.
Docker Compose продолжает использовать тот же Dockerfile; миграции не изменены.
Production Compose передаёт три параметра пула из окружения с теми же defaults;
локальный Compose позволяет задать их через существующий backend env_file.

Параметры `database/session.py` читаются через `Settings` из окружения или
`backend/.env` (окружение имеет приоритет):

| Переменная | По умолчанию | Ограничение |
| --- | --- | --- |
| `DB_POOL_SIZE` | `7` | целое > 0 |
| `DB_MAX_OVERFLOW` | `6` | целое >= 0; неограниченный overflow запрещён |
| `DB_POOL_TIMEOUT` | `10` | конечное число секунд > 0 |

Максимум — 13 соединений **на процесс**, базовый pool сохраняет до 7 свободных
соединений. Соединения создаются по мере потребности, не все при запуске.
`pool_pre_ping=True` всегда включён: проверяет соединение при checkout, но не
защищает уже выданное lock-соединение от последующего разрыва. Таймаут пула
ограничивает ожидание checkout, не длительность SQL или всей генерации.
Параметры пула независимы от `AI_MAX_CONCURRENT_GENERATIONS`; при изменении
лимита генераций пересчитайте доступную ёмкость. Увеличение числа workers
умножает предел подключений, но не глобальное число advisory slots.

Для Neon используйте **Direct Connection**, `DB_DRIVER=postgresql+asyncpg`,
поля `DB_USER`, `DB_PASS`, `DB_HOST`, `DB_PORT=5432`, `DB_NAME` и `DB_SSL=require`.
`DATABASE_URL` не используется Engine: он собирает URL из `DB_*`.
Не используйте transaction pooler для session-level locks. Реальные `.env`
не входят в образ/документацию: задавайте секреты в окружении Render.

512 МБ RAM не гарантируют возможность пяти генераций: изображения и base64/JSON
находятся в памяти, bcrypt занимает CPU. Проверяйте RSS, задержки Neon cold start,
очередь checkout и pool timeouts под реальной нагрузкой. Моки не воспроизводят
размеры ответов и сетевые условия production. Аварийное завершение процесса и
потеря lock-сессии во время внешнего I/O остаются эксплуатационными рисками.

## CORS, CSRF и будущий same-origin reverse proxy

`core/config.py` читает `CORS_ORIGINS` как JSON-массив **точных** origins.
По умолчанию список пуст: ни localhost, ни Host запроса, ни forwarded-заголовки
автоматически не становятся доверенными. Пустая строка и `[]` означают пустой
список. Разрешены только канонические HTTP(S) origins: схема + hostname +
необязательный нестандартный порт, без пути (включая завершающий `/`), query,
fragment, userinfo или wildcard. Например, порт 443 у HTTPS нужно опустить;
hostname должен быть в нижнем регистре. `null`, `*`, шаблоны поддоменов и
некорректный JSON приводят к ошибке конфигурации. Дубликаты удаляются.

Для разработки `.env.example` содержит:

```dotenv
CORS_ORIGINS='["http://localhost:5173"]'
COOKIE_SECURE=false
COOKIE_SAMESITE=lax
```

Для Render до появления реального frontend-домена:

```dotenv
CORS_ORIGINS=[]
COOKIE_SECURE=true
COOKIE_SAMESITE=lax
```

После выбора домена добавьте его реальный HTTPS origin в JSON-массив. Можно
указать несколько точных origins, но не нужно оставлять localhost в production.
Не копируйте тестовые домены из backend-тестов в production. `CORSMiddleware`
использует этот allowlist с `allow_credentials=True`, отражает только разрешённый
origin и выдаёт `Vary: Origin`. Отсутствие CORS-разрешения само по себе не
предотвращает выполнение простого POST — поэтому есть отдельная CSRF-проверка.

### Origin/CSRF: найденное состояние и текущая политика

При проверке исходного backend отдельной Origin/CSRF-защиты не обнаружено:
был только CORS. Теперь `core/csrf.py:OriginCSRFMiddleware` проверяет все методы,
кроме GET/HEAD/OPTIONS, **до** авторизации, чтения тела и бизнес-обработчика:

- Если `Origin` присутствует, он должен точно входить в `CORS_ORIGINS`.
  Запрещённый, `null`, пустой или несколько Origin дают **403** — в том числе
  при login, регистрации, logout и генерации, даже если cookies ещё нет.
- При отсутствии Origin сохранено прежнее поведение API/non-browser клиентов:
  запрос принимается, кроме явно указанного `Sec-Fetch-Site: cross-site` (403).
  Это не доказательство same-origin и не полноценная token-based CSRF-защита.
- Ни `Host`, ни `Forwarded`, ни `X-Forwarded-Host/Proto/For` не расширяют доверие.
  Совпадение Origin с внутренним Host также не даёт автоматического разрешения.
- Пустой allowlist блокирует все unsafe-запросы **с Origin**, но не закрывает
  публичный API для клиентов без Origin. CORS/CSRF не заменяют авторизацию.

**Оставшийся риск:** если браузер/прокси удаляет и Origin, и Fetch Metadata,
сервер не отличит такой запрос от совместимого API-клиента. SameSite=Lax —
дополнительная защита, но не устраняет все same-site/legacy-сценарии. После
подключения Worker убедитесь, что заголовки сохраняются. Если это обеспечить
невозможно, безопасное дальнейшее решение — требовать Origin для unsafe
cookie-запросов либо внедрить проверяемый CSRF-токен. Сейчас такое требование не
введено, чтобы не сломать существующие no-Origin клиенты. GET не проходит CSRF
проверку; существующий GET главной страницы создаёт guest cookie. Не добавляйте
на GET бизнес-операции, изменяющие пользовательские данные.

### Контракт Cloudflare proxy

Браузер обращается к HTTPS-домену frontend по `/api/*`. Worker должен:

1. Проксировать API на Render, согласованно удаляя `/api` перед существующими
   backend-маршрутами (либо корректно настраивая ASGI root_path).
2. Сохранять исходные `Origin`, `Sec-Fetch-Site`, `Cookie`, метод и тело запроса.
   Не подменять Origin значением доверенного домена для произвольного клиента.
3. Возвращать каждый `Set-Cookie` отдельным заголовком, не объединять их через
   запятую, не кешировать ответы авторизации и приватные API/изображения.
4. Не переписывать cookies в домен Render. Backend уже выставляет host-only
   HttpOnly cookies без `Domain`, `Path=/`: браузер применяет их к публичному
   frontend-host, а путь покрывает `/api/*`. Login/registration и logout используют
   тот же Path для установки и удаления user/guest cookies.

Для единого HTTPS origin достаточно `COOKIE_SECURE=true`, `COOKIE_SAMESITE=lax`;
переход на SameSite=None не нужен. Secure определяется настройкой, а не
`X-Forwarded-Proto`, поэтому внутренний HTTP-хоп не ослабляет cookie.
Не разрешайте произвольные forwarded-заголовки: Uvicorn должен доверять только
известным ingress/proxy IP, не `--forwarded-allow-ips=*`. Доверие к ним для схемы
и client IP — отдельная инфраструктурная настройка, не основание для CSRF.
До запуска проверьте реальную цепочку Render/Cloudflare и client IP (иначе IP
rate limit может видеть общий адрес прокси). Прямой доступ к Render остаётся
возможен; allowlist не аутентифицирует Worker и не ограничивает non-browser
клиентов. Ограничение direct ingress при необходимости настраивается отдельно.

Worker реализован в `frontend/worker/index.ts`. Его upstream зафиксирован на
`https://ttm-backend-du5g.onrender.com`: значение не берётся из URL, query или
заголовков клиента. Он снимает ровно префикс `/api`, поэтому frontend-запрос
`GET /api/images/{generation_id}` приходит в существующий FastAPI-маршрут
`GET /images/{generation_id}`. Все API-ответы помечаются `private, no-store`.
Локальный Vite dev proxy и nginx используют такое же преобразование пути.

Для production задайте Render-переменные `COOKIE_SECURE=true`,
`COOKIE_SAMESITE=lax` и добавьте точный Cloudflare frontend origin (без пути и
завершающего `/`) в `CORS_ORIGINS`. Иначе безопасные POST-запросы через Worker
будут корректно отклонены Origin/CSRF middleware с 403.

## Чаты и история

Используются существующие `tests.chats` и `tests.users_requests.chat_id`.
Дополнительных таблиц, миграций или повторного переноса старых генераций нет.

- `GET /Text-to-Masterpiece/chats?limit=50&offset=0` — чаты текущего владельца:
  `id`, `title` (первый prompt), `created_at`, `updated_at`. Сортировка:
  `updated_at DESC, id DESC`; `limit` от 1 до 100, `offset` неотрицательный.
- `GET /Text-to-Masterpiece/chats/{chat_id}` — все генерации чата в порядке
  `created_at ASC, id ASC`, с ID генерации, prompt, created_at и model. Чужой или
  отсутствующий чат возвращает одинаковый 404, включая доступ без гостевой cookie.
- `POST /Text-to-Masterpiece/generate` принимает необязательный `chat_id` (UUID
  или null) и возвращает `chat_id`, `generation_id`, `model_id`, `model_name`.
  При переданном ID владелец проверяется до захвата слотов, Token Bucket и бюджета.
  После успешного ответа провайдера и подтверждения загрузки в B2 новый чат и
  генерация записываются одной транзакцией, а `updated_at` обновляется. Объект
  удаляется при подтверждённом откате. При неизвестном исходе COMMIT он сохраняется
  для сверки, чтобы не удалить изображение уже зафиксированной генерации.
- При продолжении владелец дополнительно проверяется в короткой транзакции
  сохранения с блокировкой строки чата. Во время Cloudflare SQL-транзакции нет.
- Регистрация и вход переносят гостевые чаты и генерации в той же транзакции;
  гость удаляется только после переноса обеих сущностей.
- Маршрут `/chat_history` сохранён, но возвращает ID без прежнего `image_url`,
  как и история чата. Sidebar использует `/chats`,
  а выбор чата загружает весь его список генераций. Старые записи с null-моделью
  остаются доступными; frontend показывает прежний fallback названия модели.

Чат группирует результаты только для UI и хранения. Cloudflare получает только
текущий prompt и выбранную модель — без chat_id, прошлых prompt или изображений.
Ограничения владельца, глобальные слоты, Token Bucket, Neurons и deadline 60 секунд
не изменены.

Frontend сохраняет активный UUID чата и черновик в sessionStorage, повторно
загружает генерации после обновления страницы, сбрасывает ID по New chat и
очищает состояние при смене владельца. Отменённые/устаревшие запросы истории и
генерации не могут дописать результаты в другой открытый чат. При входе гостя
активный перенесённый чат загружается заново под аккаунтом.

## Тесты

`tests/test_browser_security.py` проверяет валидацию и пустой allowlist,
credentialed CORS/preflight, запрещённые простые POST, login/logout/registration,
дублированный Origin, spoofed Host/forwarded, no-Origin политику и HTTPS cookies
через тестовую ASGI-симуляцию внутреннего proxy-hop и `/api` root_path.
Существующие guest → user/history тесты также должны проходить. ASGI-симуляция
не заменяет браузерные end-to-end тесты с настоящими Worker и Render.

Из каталога `app`:

```sh
backend/.venv/bin/python -m pytest backend/tests -q
npm --prefix frontend test
npm --prefix frontend run build
```

PostgreSQL-тесты запускают временный локальный кластер (`initdb`, `pg_ctl`,
не от root). Альтернатива — явно заданный `TEST_AI_DATABASE_URL` с asyncpg URL
тестовой БД. Создаются и удаляются только случайные тестовые схемы; настройки
рабочей БД не используются. Для теста потери соединения роль должна иметь право
завершать свои PostgreSQL backend-сессии. Cloudflare во всех тестах замокан.

Проверяется конкуренция независимых физических соединений, сохранение lock после
COMMIT, одновременный захват пяти слотов через независимые соединения и pools,
503 для шестого пользователя без списания лимитов, повторный захват после
освобождения, приоритет 409 того же владельца, ошибки провайдера/хранилища/истории,
сетевой timeout и общий deadline, отмена и потеря PostgreSQL-соединения.

`tests/test_render_pool.py` синхронизирует пять сохранений и три дополнительных
запроса (login/history/models), проверяя реальный пик checkout **13** в пуле 7+6,
затем успешные ответы, сохранённые строки и освобождение соединений/слотов.
Внешние AI/B2-вызовы замоканы. Отдельный тест завершает PostgreSQL lock-сессию
после успешного B2 PUT и проверяет 503, отсутствие записи и удаление объекта.
Все lock PostgreSQL-тесты используют ограниченный пул 7+6 с pre-ping.

Локальная проверка: **250 тестов пройдены**, включая запуск всего набора в
systemd scope с `MemoryMax=512M`, `MemorySwapMax=0`. Пиковый RSS процесса pytest
— 240732 КиБ, `memory.peak` scope — 218914816 байт, OOM/OOM kill — 0.
Это pytest + ASGITransport и временный локальный PostgreSQL, не production
Uvicorn и не нагрузка с настоящими размерами изображений; результат не является
гарантией укладывания production в 512 МБ. Для повторения из `app`:

```sh
systemd-run --user --scope -p MemoryMax=512M -p MemorySwapMax=0 -- \
  backend/.venv/bin/python -m pytest backend/tests -q
```
